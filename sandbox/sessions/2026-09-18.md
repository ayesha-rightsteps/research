## 4. Design decisions

**Warm-start dono critic heads duplicate karna, random se start nahi
karna:** Root cause fresh-critic + converged-actor mismatch tha — is fix ke
alternatives the (a) actor ko bhi fresh start karo (poora restart, bahut
zyada waqt lagta), (b) critics ko chhote learning rate se "warm up" karo
training shuru hone se pehle (extra complexity). Duplicate-from-old-single-
critic sabse simple aur direct fix hai — dono heads ko ek reasonable
starting point milta hai (jo already is env/task pe train ho chuka hai),
phir naturally apne-apne reward stream ke hisaab se diverge karte hain.

**Sirf seed 42 pe pehle test karna, poore 5-seed run se pehle:** Pichle
session (2026-09-17) mein config-mismatch bug ka lesson — bina verify kiye
"fix" ko poore run pe commit karna Kaggle time waste karta hai agar fix
adhoora nikle. Is baar 1-seed (~44 min) sanity check pehle, phir hi 5-seed
(~3.7h) commit karenge.

Poore session ke evidence (single-critic aur two-head dono, coef 0.15/0.30/
0.45 sab) ko dekh ke ek deeper diagnosis nikla:

**Do forces har gradient step pe compete karte hain:**
1. **Actor loss** — poore batch (mostly safe states, danger-close bahut rare)
   se average gradient. Training data mein generally `A_mission > A_safety`
   dikhta hai, isliye actor loss ka natural pull **hamesha upar (mission-
   focus)** hai — safe ho ya danger, dono jagah.
2. **Prior loss** — sirf danger-close samples ko heavy weight deke neeche
   khینchta hai.

**Jo bhi danger-close moments pe jeetta hai, wahi α lock ho jaata hai** —
ek baar entropy collapse ho jaye (har run mein hota hai), danger-close
states rarely visit hote hain, correction ka mauka bhi kam ho jaata hai.
**Ye gradual learning nahi, ek lock-in hai.**

**Seed-dependent kyun hai:** Har seed ki early-training trajectory (random
action sampling se decide hota hai kaunse states pehle visit honge) alag
hoti hai — chhoti initial randomness decide karti hai is race mein prior
jeetega ya actor loss, entropy collapse se pehle. Ye ek chaotic/bistable
system hai (do stable outcomes — sahi-lock ya galat-lock) — kaunsa milega
smoothly predictable nahi hai.

**Isiliye `prior_coef` badhane se clean improvement nahi mila:** Higher
coefficient ne kuch seeds (45, 46) ka race outcome flip kar diya (sahi
direction mein), lekin doosre seeds (42, 43, 44) ki poori training dynamics
bhi badal di (bigger early gradients se episode 1 se hi alag trajectory) —
aur unhe **galat basin mein bhej diya**, jabki wo pehle naturally sahi lock
ho rahe the. Same coefficient, alag seed = alag race outcome.

**Conclusion:** `prior_coef` ek global knob hai jo *kis basin mein girega*
uski probability shift karta hai, guarantee nahi deta. Single-number tuning
se pura fix nahi hoga — architecture ko is race ko directly rokna padega.
